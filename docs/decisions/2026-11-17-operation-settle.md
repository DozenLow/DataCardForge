# 决策：防抖属于用户操作——全工作区一个 200ms 结算

- **日期**：2026-11-17
- **状态**：✅ 已实施（`operationSettle.ts`；公式卡 250ms、脚本卡 500/600ms 已删除）
- **标签**：`#前端 #交互 #防抖 #数据流`
- **结论**：防抖不是计算节点的事，是**用户操作**的事。全工作区只有一个 200ms 静默期；
  会影响其他卡片的定义编辑在静默期结束时一次性提交，随后整条链立即执行，中间卡片不再
  各自等待。离散动作（运行、换文件、建卡、改名确认）先 `flush` 再执行，绝不等待打字停顿。
- **上游决策**：[卡片数据结构 v2](2026-10-26-card-schema-v2.md)（编辑 = 一次 PATCH）、
  [Python 脚本卡](2026-11-15-python-script-card.md)（定义与检查的节奏）

## 核心表述

> 用户停手 200ms，就当作"这次操作完成了"；从那一刻起，前端只负责把这一次操作送下去，
> 后端一次评估整棵子树。没有哪张卡在链中间再等一次。

## 背景（这一轮修的是什么）

改动前有三个互不相干的定时器：公式卡 250ms、脚本卡定义同步 500ms、脚本卡权威检查
600ms。它们都长在"卡片"上，于是：

| 现象 | 原因 |
|---|---|
| 在一张卡里打字，另一张卡的改动跟着变慢 | 每张卡各自重置自己的计时器 |
| 同一暂停里编辑两张卡，产生两波计算 | 计时器不共享 |
| 点"运行"可能跑的不是屏幕上的文本 | 500ms 内点击会读到旧定义 |
| 自动运行如果再加一个防抖，就是第四套延迟 | 延迟被当成节点属性 |

用户的要求：防抖只属于操作；操作结束后一次性往后执行；中间不等待。

## 决策内容

1. **一个全局静默期**：`settleOperation(key, task)` 每调用一次就重置同一个 200ms 计时器；
   同一个 key 的新任务**替换**旧任务（一次按键不会排队两次提交）。计时器是模块级的，
   卡片卸载不会丢掉待提交的编辑；任务发现卡片已关闭时是 store 的 no-op。
2. **结算后一波发下去**：脚本卡的 `setScriptText` 与权威检查在同一个任务里；公式卡的
   表达式提交在同一个任务里。后端 PATCH 之后同步评估子树，所以中间卡片没有自己的等待。
3. **离散动作先 `flushOperations()`**：运行/调试（含 Ctrl/⌘-Enter）、端口/输出改名、增删
   端口输出、从输出建卡、公式卡重算与建图、换文件/重指向。语义是"我操作完了，立刻按
   我看到的状态执行"，不与打字停顿赛跑。
4. **外部重写用 `cancelOperation`**：改名会改写编辑器文本，此时待提交的是改名前的文本；
   先取消它，再由编辑器同步改名后的文档（改名本身在调用 store 动作前已 flush）。
5. **自动运行不新增防抖**：触发信号是脏节点，结算只属于用户操作（见
   [脚本卡自动运行](2026-11-17-script-autorun.md)）。
6. **不在此机制内的延迟**：`useAccuracyHint` 的 3s 是一次**测量**的推迟（精度抖动），
   不是传播防抖，保持不动。

## 不变量（改这块时不许破）

- 全工作区只有一个结算计时器；不得在卡片/节点里各自加计时而绕过它。
- 同 key 覆盖、不排队；一个打字 burst 只产生一次定义提交与一次权威检查。
- 离散动作执行前必须 flush；flush 期间新调度的任务进入下一个周期，不被本次 flush 吞掉。
- 自动运行与下游传播不引入新计时器：结算之后只有网络与后端计算。
- 外部改写文本前必须取消该卡待提交的任务，否则旧文本会覆盖改写结果。

## 门禁

- `web/tests/operationSettle.test.ts`：静默期 200ms、同 key 覆盖、全局共享、flush 立即且
  取消计时、flush 期间新任务另起周期、单 key 取消、重置。
- `web/tests/ScriptCard.dom.test.tsx`：burst 只发一次检查（199/200ms 边界）、本地层仍然
  0 延迟、无尾随第二次请求。
- 浏览器实测：连续输入后 **1 次 PATCH（200ms）**、**1 次 `/api/script/check`（199ms）**。

## 未决（下一轮）

- 权威检查与定义提交共用 200ms 后，打字停顿会多 spawn 一次 CPython（compile-only）；
  如果实测成本明显，可让检查单独用一个更长的周期（但那会打破"一个结算"的单一规则，需要
  新决策）。
- 结算目前不区分"焦点在哪个卡"：在两张卡之间快速移动会合并成一波。这是有意的，但值得
  在真实工作流里观察一次。
