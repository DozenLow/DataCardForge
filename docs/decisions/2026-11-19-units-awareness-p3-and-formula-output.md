# 决策草案：单位感知阶梯 —— P3「提示」与「公式输出单位」的统一规划

- **日期**：2026-11-19
- **状态**：📝 **草案 / 讨论中，未实施**（本文只论证与规划，不含任何代码改动；拍板前不动契约）
- **标签**：`#单位 #函数卡 #量纲 #P3 #草案`
- **上游**：[单位 v1](./2026-11-18-units-v1.md)（🔒 已定稿：单位=派生元数据、不做量纲代数）、
  [任务书 P3](../tasks/2026-11-18-units-v1.md)（提示，未做）
- **结论（待拍板）**：P3 的「单位提示」与「公式卡输出丢单位」是**同一个量纲推断能力的两个消费方**，
  不应各自实现。建议按「推断阶梯」L1→L2→L3 分期：先做**便宜且诚实**的 L1（换文件漂移提示 +
  显式输出单位 + 仅对可直接解析操作数的加法提示），再视需求做 L2（安全白名单继承），L3（完整量纲代数）
  仅在真实需求触发时启动。**任何一级都只声明它能证明的，证明不了就不声明（=v1 的丢弃行为），故逐级严格 additive、永不撒谎。**

## 一、两个观察到的缺口

1. **P3 未做**：任务书 P3 = ① 表达式 `+ - 比较 IF` 两侧量纲静态检查，成功响应加 `warnings`（纯增量、不改数值）；
   ② 换文件时同名列单位漂移走现有提示流；③ 每工作区「宽松模式」开关。验收要求 xlayer 夹具零改动。
2. **公式卡输出丢单位/量纲**：输出列 `annotation` 是**公式名**（`nodes.cpp` `col.annotation = name`，如「时间_s × 2」），
   解析不出单位 → `unknown`。表达式引擎单位盲（纯 double），v1 明确不做量纲代数。
   对照摘要卡**逐字继承**源 annotation（保留单位），口径不一致。

下游后果：P1d 轴单位（仅全列 recognized 才显示）对公式输出致盲；换算卡对公式输出 `from` 解析失败；
测量溯源在变换后静默丢失。

## 二、「丢」是否合理：分情况

- **合理/安全的一面**：任意表达式的输出量纲是整棵树的函数。截图公式 `时间_s * 油门开度_pct` = s·%（复合量），
  不完整的传播器若标成「s」或「%」就是**错误声明**，比不声明更糟。输出常是「新量」（得分/特征），本无物理单位。
  丢弃是 v1「不做量纲代数」显式范围的直接推论，且损失局部（源卡单位仍在）。符合「绝不静默误导」底线。
- **不合理的一面**：对**可证明保单位**的变换（`col*k`、MOV/EMA、ABS、AVG/MEDIAN…）也一刀切丢弃，属过宽的
  needless loss；下游单位链路在公式卡断掉；与摘要卡继承口径不一致。
- **判断**：作为 v1 保守范围合理；作为「单位感知测量工作台」的产品承诺是真实缺口。
  对复合/歧义表达式丢=正确；对保单位变换丢=浪费。合理性取决于产品承诺到哪一层。

## 三、统一视角：一条量纲推断阶梯

P3 的加法检查需要知道操作数量纲；公式输出单位需要知道结果量纲。**二者共享同一推断机器**，分开做会重复建设。
阶梯每一级只比上一级多证明一点，证明不了就回落到「不声明」（v1 行为），因此**严格 additive、可独立验收**：

| 级 | 推断能力 | 解锁的消费方 | 成本 | 契约影响 |
|---|---|---|---|---|
| L0（v1 现状） | 无（仅输入派生元数据） | 表头 chip、组级确认、换算卡（显式 from） | 已完成 | 无 |
| L1 | 仅**直接可解析**的操作数（直列引用）+ 用户**显式断言** | P3②漂移提示；P3①加法提示（仅直列操作数，嵌套不报=诚实）；**公式显式输出单位** | 低 | 纯增量：`warnings` 通道、`params.formulas[].unit?` |
| L2 | **安全白名单**保单位变换的继承（标「继承」） | 输出单位自动继承（`col*k`/MOV/EMA/ABS/AVG…）；加法提示扩展到可解析子式 | 中 | 增量；白名单需夹具钉死 |
| L3 | 完整量纲代数（指数向量贯穿 +−×÷^ 与函数单位表） | 输出量纲自动推导、完整提示、换算自动建议 | 高 | **动「不做量纲代数」冻结决策 + 跨层 oracle** |

要点：
- **L1 的加法提示只报「能证明的」**：`A + B` 两直列单位已知才比；`(A*B)+C` 左操作数不可解析则**不报**（不猜）。
  这与「不撒谎」一致，也避免 L1 被迫做代数。
- **显式输出单位是用户断言**，不是推导：诚实、便宜、立刻接通轴/换算。字段放 `params.formulas[].unit?`
  （参数归签名，additive）。
- **L2 白名单必须可证明**：`SIGN` 返回无量纲、`SQRT` 是 ^0.5、`COUNT`/`SUM(A>5)` 变计数——这些**不在**保单位白名单。
  白名单用共享夹具钉死，C++/TS 同判。
- **L3 触发条件**（仿脚本卡分期）：出现「必须自动推导复合量纲」的真实用户需求，且 L1/L2 已被证明不够；
  同时需决策跨层 oracle 去留（TS 参考实现要么镜像代数、要么退役）。

## 四、建议分期（待拍板）

1. **P3-L1a（最便宜，先做）**：换文件同名列单位漂移提示（纯元数据对比，无代数）+「宽松模式」开关。
2. **P3-L1b + 显式输出单位**：`warnings` 增量通道 + 直列操作数加法提示；公式输出可选 `unit` 字段（用户断言），
   接通 P1d 轴与换算卡。验收：xlayer 零改动、新增 `fixtures/units/warnings.json`、显式单位 dom 测试。
3. **L2（视需求）**：安全白名单继承，标「继承」；白名单夹具双边钉死。
4. **L3（仅触发时）**：完整代数，另开决策。

## 五、风险与不变量（贯穿各级）

- 数值永不自动改写；提示**只建议不阻塞**（宽松模式可关），与 v1「标注而不拦截」一致。
- 任何单位声明必须可证明或用户断言；继承要标「继承」，推导要标「推导」，不冒充源单位。
- L1/L2 不动 DCM2、不动表达式语义、xlayer 夹具零改动；L3 才碰冻结契约。
- 提示/单位字段全部 additive，旧工作区/旧后端可读。

## 六、开放问题（拍板项）

1. 显式输出单位放 `params.formulas[].unit?` 是否合适？是否允许「继承自源列」作为快捷选项？
2. 加法提示默认开还是关？「宽松模式」语义=自动换算还是仅静默提示？（倾向仅静默提示，不自动改数）
3. L2 继承默认自动（标「继承」）还是需用户 opt-in？
4. L3 的触发条件与跨层 oracle 去留，是否现在写死还是留待需求？

## 七、验收信号（分期）

- L1a：换文件漂移提示 dom 测试；宽松模式开关持久化。
- L1b：`warnings.json` 双边夹具（直列 mismatch 报、嵌套不报）；显式单位接通轴/换算 dom 测试；xlayer 零改动。
- L2：白名单继承夹具（含 SIGN/SQRT/COUNT 反例不继承）。
- L3：另行决策与夹具。
